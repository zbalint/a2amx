## 1. Why

The owner set both thresholds of the watcher (`activity = { working_after, idle_after }`) to 15 seconds and received `- junior-developer: idle (was working)`, `- tester: idle (was working)` and `- consultant: idle (was working)` right after a team start, though no peer had done any work. The cause is `session_working` (`src/daemon/views.rs:328`): it says `!ready || unchanged < ACTIVITY_QUIET`, so a session that has not yet shown its ready screen is working. Booting Claude, Codex and OMP sessions take longer than 15 seconds, so the tracker (`src/activity.rs`) settles `working` as the peer's first state (silently, by design), and the later `idle` is announced as a change.

`Session::starting()` (`src/session.rs:239`, introduced by spec 3aw for the status dot) already says exactly "this session has never shown its ready screen": the latch is set the first time `harness::ready` is true, never cleared, and `starting()` is false for Generic and Agy sessions and for exited ones. The activity notices never read it.

Alternatives rejected while grilling:

- A new `starting` word in `Activity` (wire, `a2amx list`, `list_agents`, status line): a wire change that needs client and daemon upgraded together, and the dot already shows `starting` from the existing `SessionSummary.starting` field. The list keeps reporting `working` for a booting session, which is the safe reading for the architect's "send only when every peer is idle" gate.
- Skipping the first working to idle transition of every peer: a session launched with a task is working from its first moment, and its first idle is the notice the architect waits for.
- Treating a starting session as idle (`Some(false)`): the tracker would settle `idle` during boot and announce a `working (was idle)` notice for the post-boot screen draw.

## 5. Out of scope

- A visible `starting` activity word in lists, `explain`, `list_agents` or the status line; the dot already shows starting. A later spec could add it as a wire change.
- Agy and Generic: `starting()` is false for both by spec 3aw's decision, so their boot still reads working. An agy peer whose boot is shorter than `working_after` never announces anything, which is what the owner saw.
- The boot after `reset_session`: the latch is not cleared by a reset (spec 3aw), so a reset peer's boot still reads working and can produce an idle notice. Backlog item to raise with the owner if it shows up.
- The tracker, the thresholds, the quiet window, the heartbeat digest (`observe_peers` uses `session_activity`) and the picker.
- The rule that a peer's first settled state is silent stays: a session launched with a task goes starting, working, idle, and the watcher is told only the final `idle (was working)`, not a `working` notice at the start.
