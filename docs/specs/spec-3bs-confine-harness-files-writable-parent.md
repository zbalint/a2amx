## 1. Why

A confined Claude session cannot renew its login: after the 8-hour access token expires, the session gets a 401, and `/login` from inside the session does not work either. Reproduced on 2026-10-31 with the installed Claude 2.1.316 and bubblewrap 0.11.1 on scratch homes (memory `f3da77b9`):

| Experiment | Mounts | Result |
| --- | --- | --- |
| `claude mcp add` (writes `~/.claude.json`) | A: parent read-only, file bound writable (today) | refused: "was not saved ... protected by a sandbox" |
| same | B or C: parent writable (tmpfs or real), file bound or not | saved; with a bound file the rename fails with EBUSY and Claude writes in place |
| same | D: `--overlay-src DIR --tmp-overlay DIR`, file bound on top | saved; siblings visible; other writes discarded at exit |
| refresh of a fake expired token (`claude -p hi`, the server answers 400) | control, no sandbox | `OAuth refresh failed (expected): ... 400`: the refresh reached the network |
| same | A (today) | no refresh line: the refresh aborts before the request; 401; config saves fail on `<home>/.claude.json.lock` (EROFS) |
| same | overlay on `~/.claude` only | the refresh reaches the network (400); `OAuth refresh legacy-lock acquire failed: EROFS, mkdir <home>/.claude.lock` at DEBUG level, non-fatal; config saves still fail |
| same | overlay on the whole home | refresh reaches the network, config saved in place, no lock errors |

Claude takes a refresh lock inside its config directory (`<config dir>/.oauth_refresh.lock`), a legacy lock beside it in `$HOME` (`<config dir>.lock`) and a `<file>.lock` for every config save in `$HOME`; it saves files by a temp file next to the target and a rename, falling back to an in-place write for EPERM, EBUSY and EACCES but not EROFS. a2amx binds the harness data files singly inside read-only directories (`harness_data`, `src/confine.rs:354`), so a read-only parent aborts the refresh. The fix is shape D for the parent directory of each harness data file: the directory is writable but ephemeral, the bound files persist, nothing else the agent writes there reaches the real directory. It needs no knowledge of one harness's write pattern, so it holds for every harness (Claude: `~/.claude`; OMP: `~/.omp/agent` and `~/.omp`).

**What this fixes and what it does not (owner decision, option 1):** renewal of the access token should work; the write of the renewed token into the bound credentials file was not exercised (it needs a real token) and uses the same helper family as the config write above. `/login`, trust dialogs and every other save to `~/.claude.json` still fail inside a session, because their lock and temp files live in `$HOME`, which stays read-only (backlog F59). The refresh token lives weeks (on the owner's machine it expires 27 days after the last refresh), so the user logs in once in a normal terminal and every session shares the login.

## 2. Parents of harness data files (`src/confine.rs`)

`harness_data` returns the data directories and data files. Add `harness_overlay_parents(...) -> Vec<PathBuf>`: the canonical parent of each entry of the data-file list, deduplicated, kept only when it exists as a directory. The Claude list always names `.credentials.json`, `history.jsonl`, `stats-cache.json` and `~/.claude.json` whether or not they exist, so the parent is `~/.claude` even before a first login; OMP names the databases found at plan time (parents `~/.omp/agent` and, for `stats.db`, `~/.omp`); with no database found there is no overlay for that parent and a first database still fails loudly, as today. Excluded: the home directory (so `~/.claude.json` is not covered); and any parent that is, or lies inside, a path of `writable`, `hidden`, `readonly` or `protected` (an explicit `write`, an operator `hide`, an `unhide`, a data directory, a protected launch input). Compute the list inside `finish()` (`:1119`, which builds `protected`), after the hides and operator lists are known and before the entries below are added, so an equal-key collision in `mounts()` (a `BTreeMap` keyed by path) cannot happen: where a parent is excluded the other kind wins. Nested overlays (`~/.omp` and `~/.omp/agent`) are allowed; each lower layer is the host directory (probed).

Keep the list and the entries below in their own `Plan` fields (`overlay_parents`, `overlay_protected`), never in `writable` or `protected`: `tests/confine.rs:1687-1838` asserts that `~/.claude`, `~/.omp` and `~/.omp/agent` are not in `writable`, and `without_overlays` (section 4) must restore exactly today's mounts.

Re-protect the control files. For each overlaid parent, every existing top-level entry that is a regular file or a directory (not a symlink) and is not a data directory, a data file, another overlay parent or a hidden path goes into `overlay_protected`, mounted read-only on top of the overlay (`--ro-bind-try`, so an entry that disappears between planning and the mount does not fail the start; probed). So `settings.json`, `settings.local.json`, `plugins/`, `~/.omp/config.yml`, `~/.omp/extensions/` and the like stay read-only for the session, as `tests/confine.rs:1759-1771` pins today. **Symlink entries are not re-protected:** a bind onto a symlink fails the whole start, and a bind on its canonical target leaves the link replaceable while making the target read-only (probed); on the owner's machine `~/.claude/hooks`, `~/.claude/agents` and `~/.claude/CLAUDE.md` are symlinks into `~/.agents`, so inside a session the agent can replace them (the change is discarded at exit). That residual is documented (sections 4 and 7). Entries created on the host after planning are unprotected, and entries the agent creates are writable but discarded at exit.

`mounts()` adds each parent as `MountKind::Overlay`, and the entries as read-only mounts of their own kind; the depth sort places the overlay before every bind inside it, and `Overlay` takes rank 0 with `Tmpfs` and `Empty` at the tie-break (`:1218-1230`). `Plan::wrap` emits `--overlay-src <path> --tmp-overlay <path>` for it with no `--remount-ro` (a `--remount-ro` on the overlay path would make it read-only; the later `--remount-ro` of the hides is unaffected, probed). The hides inside the parent (`~/.claude/ide`, the credentials default hide for other harnesses) are mounted after it and still win. Put a `// shortcut: tmpfs upper layer, no size bound; bubblewrap offers none with --tmp-overlay, a disk-backed upper or a quota if it ever does` comment where the argument is emitted.

## 3. Data files missing at start, and the notice

`plan()` runs before `ensure_data_dirs` (`daemon.rs:384-386`) and `ensure_data_files` never creates a credential or database file (`:482`). A data file of an overlaid parent that does not exist at plan time is not bound, and a write to it (a first Claude login or history file) lands in the overlay and is lost at exit, silently. Add two public `Plan` accessors, `overlay_parents() -> &[PathBuf]` and `unsaved_files() -> Vec<PathBuf>` (data files of an overlaid parent that do not exist at plan time, excluding the `-wal` and `-shm` of an existing database, which `ensure_data_files` creates after planning, and excluding `~/.claude.json`, whose parent is the home and fails loudly). Both the agent notice (`confine::notice`, `:1517`; it ends with "Everything else is read-only" at `:1567-1569`) and the dry run (`src/main.rs:1130-1160`, assembled from `Plan` fields) use them. Notice lines, added to the existing "Skipped missing paths" line, not replacing it: for the parents, "<P>: writable, but only the harness's data files are saved; other writes are discarded at exit"; for the unsaved files, "not present at start, writes to them are not saved: <paths>". The dry run prints `overlay: <path>` and `unsaved: <path>` lines and makes no capability claim (it never resolves bubblewrap).

## 4. Capability: `--tmp-overlay` needs bubblewrap 0.8 (`src/confine.rs`, `src/daemon.rs`)

`plan()` always computes the overlay parents (pure, testable). Add `pub fn supports_tmp_overlay(bwrap: &Path, parents: &[PathBuf]) -> Result<(), String>`: the `preflight` argv plus `--overlay-src P --tmp-overlay P` for each parent (the plan's own parents, not `/tmp`: overlayfs support depends on the lower filesystem), then `true`; `Err` carries bubblewrap's first stderr line. Call it once per confined start after `plan()` (`daemon.rs:384`, where the plan and the resolved bubblewrap path are both held in the same blocking task), only when the plan has overlay parents. On `Err`, call `Plan::without_overlays(self, reason: &str) -> Plan`, which clears `overlay_parents` and `overlay_protected` (the other sets are untouched by construction, so the mounts are exactly today's) and sets one notice line: "harness login cannot be renewed in this session: <reason>; bubblewrap 0.8 or newer is needed (or open the harness directory with `write`)". The session still starts; never silently weaker. `Host` and the `plan()` signature do not change.

## 5. Docs (`docs/confinement.md`, `docs/harnesses.md`)

A new section in `docs/confinement.md`, "Harness login and state files", covering plainly, in this order: (1) what a confined Claude or OMP session does with its login: it shares the real login file with every other session; the directory it lives in is writable but temporary, so the harness can renew its token and save its own files, and everything else it writes there (settings, hooks, skills, new files) is discarded when the session ends and never reaches the real directory. (2) What does **not** work: `/login` and every save to `~/.claude.json` from inside a session (they need lock and temp files in your home, which stays read-only); how to log in: run `claude /login` once in a normal terminal, every session picks it up; the refresh token lasts weeks, and an expired one needs the same. (3) What the agent can still do: existing settings, plugins and other files in that directory stay read-only, but symlinked entries (for example `hooks`, `agents` or `CLAUDE.md` linked into another directory) cannot be pinned and can be replaced inside the session, also discarded at exit; entries added later are writable until exit. (4) Files that do not exist at start (a first login) are not saved; the notice and the dry run say so. (5) Several confined sessions do not exclude each other while renewing (each has its own lock): renewals that happen together may need one session restart; Claude re-reads the saved login after a 401. (6) bubblewrap 0.8 or newer; an older one keeps the previous behaviour with a plain notice line. (7) The overlay uses memory (a tmpfs, no size bound). (8) The opt-in grant that makes the config directory persistent is a separate item (spec 3bt, not yet available); until then `write = ["~/.claude"]` does it. Update the "What stays open" residual that says `~/.claude/settings.json` hooks are writable so it matches (read-only unless symlinked) and the Read-only row of the table. `docs/harnesses.md`, section "Confinement and harness boundaries": one line pointing to the new section.

## 6. Tests (`tests/confine.rs`)

1. `claude_data_files_parent_gets_an_overlay_before_the_binds`: `Plan::wrap` argv for a Claude fixture home with `~/.claude/.credentials.json`, a regular `settings.json`, a `plugins/` directory and a symlink `hooks` -> a directory elsewhere: the argv contains `--overlay-src P --tmp-overlay P` for `P = ~/.claude`; its index is smaller than the index of every bind and read-only bind of a path inside `P`; no `--remount-ro` for it; `settings.json` and `plugins` are mounted read-only after it with `--ro-bind-try`; the symlink `hooks` and its target are not mounted at all (the target is not read-only because of the plan). Any change to what is hidden. **To verify after implementation, not by this spec:** that a real renewal writes the new token into the credentials file and that two confined sessions renewing together recover (the tester can do the first with the owner's consent, never against the real login without it).

## 8. Trust boundaries

The overlay is planned from the daemon's own table, not from client input; `write`, `hide`, `unhide` and grants are untouched. Attack paths and dispositions: (1) an overlay re-exposing a hidden directory or overriding a read-only or writable mount at the same path: removed (section 2 excludes those parents; test 2). (2) The agent rewriting the harness's control files inside the session (settings, plugins) now that the parent is writable: removed for existing regular files and directories by the read-only re-mount (tests 1 and 5); **residual** for symlinked entries (replaceable inside the session, so the agent can for example swap a hooks directory that `settings.json` names), for entries created later, and for entries created on the host after planning; all discarded at exit; documented (section 5). (3) Memory: the upper layer is bubblewrap's tmpfs, sized by the kernel default (half of RAM per overlaid parent; `--size` is refused with `--tmp-overlay`, probed): accepted with the `shortcut:` comment of section 2, because a session can already allocate memory directly and the confinement is a seatbelt, not a resource limit. (4) Silent loss of writes to files missing at start: disclosed in the notice and the dry run (section 3). (5) No cross-session exclusion while renewing: documented (section 5).

## Amendment 1 (2026-10-31, consultant `m_4893`, applied while the developer implements; documentation and disclosure only)

A single-file bind on top of the overlay pins the file's inode (probed by the consultant). When an unconfined harness renews its login by writing a temp file and renaming it over the credentials file, a running confined session keeps the old file: it reads the old token, and its own later writes go to the replaced inode and are lost, so a confined session can end up logged out although the host file is valid. This is not new (before this spec the same pinning applies and writes fail loudly), and a2amx cannot change how the harness replaces the file; this spec disclaims it instead:

- `docs/confinement.md`, the new section "Harness login and state files": add to item (2) that logging in or renewing **outside** a session replaces the login file and a running confined session keeps the old copy, so **restart the confined sessions after you log in outside**; add to item (5) that a confined session that renews while an unconfined harness of the same account also renews can end up logged out and needs the same restart. The section 5 list in this spec gains these two clauses; nothing else in it changes.
- Section 8 gains attack-path-free residual (6): "an unconfined renewal strands the confined sessions' login file until they restart; documented".
- Section 7 "To verify after implementation" gains: that a host-side rename over the credentials file leaves a confined session with the old content (expected, documented).
- No code, test or scope change. The developer adds the two clauses to the docs it is already writing and reports it.
