## 1. Why

The feature works end to end in code, but a user cannot find out how to set it up: no page names the Discord side (bot, intents, private server), the commands (`gateway token`, `gateway up --pair`, `new --remote`, the code `team up` prints), the files, the sandbox, the firewall note, or the risks. `docs/permissions.md` still says the gateway process is not built, and `docs/cli.md` and `docs/teams.md` do not mention `--remote`, the `remote` setting or `gateway`.

The page is a how-to with reference tables (project-docs: one page, linked from the README). Alternatives rejected: one page per step (the steps are short and run in one order; splitting hides the order); putting the setup in the README (the README is a landing page; the move rule sends technical detail to `docs/`).

Honesty requirement: the Discord setup steps have not been run against the live Discord portal, and the gateway has not run against real Discord (the owner's live test comes after this spec). The page says so in a "Status" note at its top, which contains the exact phrase "not yet tested" ("The Discord setup steps and the gateway against a real Discord server are not yet tested with A2AMX"), and marks the Discord portal section with the same phrase. It claims nothing about Discord behaviour that the code or the fake-Discord tests do not show.

## 2. Page outline: `docs/remote-messaging.md`

Title "Remote messaging". Sections in this order; each fact is checked against the code before it is written (sections 4 and 7).

1. **What it is and is not.** An agent on a long task messages the paired human on Discord, and with `both` the human writes back. Messaging only: no terminal output, no remote control, no attachments, no direct messages with agents. Discord text is not end-to-end encrypted: Discord and everyone with access to the server can read it. Off by default, per agent, confined sessions only. The "Status" note (section 1) goes here.
2. **What you need.** Linux, `bwrap` (the gateway refuses to run without it and never runs unconfined), a running daemon, confined sessions, a Discord account and a private server you own. Codex sessions cannot be confined, so remote messaging is not available to Codex agents. The server has no invite link and `@everyone` is trimmed (remove Create Invite, Mention @everyone and other defaults the agents do not need; check the bot's granted permissions on the server's Integrations page); the bot is the only other member. The gateway compares Discord's approximate member count with `max_members` (default 2: you plus the bot): above the limit at startup it exits, and afterwards it pauses; it re-checks every 60 s by default, and a failed check changes nothing.
3. **Set up Discord** (numbered steps; from Discord's documentation, not yet tested): create an application and a bot; enable the Message Content privileged intent (the gateway asks for the guilds, guild messages and message content intents); copy the bot token; create a private server; invite the bot with the permissions Manage Channels (it creates the categories and channels), View Channels and Send Messages (Read Message History is not used: messages arrive over the websocket, nothing reads history); copy the server id (developer mode). Tell the reader to treat the token as a password and to reset it if it leaks.
4. **Configure the gateway.** `a2amx gateway token` (reads the token from standard input; the echo is off on a terminal; stored 0600 as `<state>/gateway/discord.token`); `<state>/gateway/config.toml` with the keys table (key, default, meaning) taken from `src/relay_files.rs`: `guild_id` (required), `control_category`, `control_channel`, `max_members`, `sync_ms`, `idle_ms`, `member_check_ms`, `reconnect_ms`, `api_base`, `gateway_url` (the last two are for tests: leave unset). Unknown keys are rejected. `guild_id` is 1 to 20 digits; `control_category` and `control_channel` are lowercase letters, digits and `-`, starting with a letter or digit; every `*_ms` value is at least 1. The reader creates `config.toml` themselves, so the page shows a creation command (for example `install -m 600 /dev/null <state>/gateway/config.toml`, then edit). Files must be owned by the user, regular, with no group or other permissions (create them 0600), at most 64 KiB, and not symlinks.
5. **Pair your Discord account.** `a2amx gateway up --pair` creates the control category and channel, prints a code, the reader posts it in the control channel, and the terminal asks to confirm the account; pairing is saved to `pairing.json`. `--pair` needs an interactive terminal (the prompt reads `y`/`yes`); the code expires after 10 minutes, and declining the prompt ends with "pairing not confirmed". The gateway answers only the paired account. Later runs use `a2amx gateway up`.
6. **Start the gateway.** The daemon runs first. `gateway up` checks that `link/addr` and `link/gateway.token` exist as regular files and says the daemon is not running when they are missing; after a daemon crash they can be stale, and the relay then exits at startup with a connection error (the first connection to the daemon is not retried). Once connected, a daemon outage does not stop the relay: it marks the daemon unreachable, answers the paired account "a2amx is not reachable right now", and reconnects through `link/` every `reconnect_ms`. What appears in Discord: the control category and channel at once, and a category per team and a channel per agent only once the lease has started (the gateway lists agents that have `remote` set, are confined and have a valid lease; within `sync_ms`, 15 s by default). Stop with Ctrl-C (clean) or SIGTERM (immediate).
7. **Turn it on for agents and start the lease.** the team file `remote` setting per session (`send` or `both`; confined sessions only; the team file needs a team name). `a2amx new --remote` only marks a session; a session outside a team never reaches the gateway, because leases and the gateway's agent list are per team. `a2amx team up` prints the agents it enabled and a single-use code that is valid for 10 minutes; the reader posts the code in the control channel; the gateway answers "remote messaging is on". Five wrong codes (counted across the whole daemon) clear every pending code. The lease lasts at most 24 hours, is in memory, and covers the team members at the moment the code is redeemed; an agent restarted or added afterwards is not covered until a new code is posted. It ends when its member sessions exit (team down) or the daemon stops, since nothing clears it explicitly. After a daemon restart the reader needs a new code. Say what `send` and `both` mean and how an agent addresses the human (`send_message(to="human:owner")`).
8. **What the sandbox does.** A table "the gateway can see / cannot see": it can read and write `<state>/gateway/` and a 1 GiB temporary `/tmp`, read `<state>/link/` (the daemon's address and the gateway token), read `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc` and its own executable, plus the one file `/etc/resolv.conf` points to when that lies outside `/etc` and `/usr` (for example under `/run/systemd/resolve` or `/mnt/wsl`), and see its own processes only (`/proc` in its own PID namespace) and a minimal `/dev`; it cannot see `admin.token`, the rest of the state directory, the home directory, the rest of `/run`, `/var`, `/opt`, or other users' files; the environment is cleared except `PATH` and `RUST_LOG`. Then the **firewall note**: A2AMX does not filter the gateway's network traffic. If the host has a firewall or proxy, allow `discord.com` and `gateway.discord.gg` for the gateway (the websocket may be redirected to another `*.discord.gg` host, which comes from Discord's documentation and is not yet tested); the sandbox shares the host network.
9. **Limits and residual risks.** Rate limits (human to agents 20 a minute, all agents to the human 30 a minute, each agent 20, a human message at most 8000 bytes); the member-count pause; and the residual risks, each in one sentence: abstract unix sockets and loopback TCP stay reachable from the sandbox because the network is shared; the sandbox does not use a new terminal session, so on a kernel that still allows `TIOCSTI` a compromised gateway could push input into the terminal it was started from (start it from a terminal whose input you do not mind exposing, or with `setsid`); Ctrl-C stops the relay cleanly and SIGTERM stops the gateway at once without a clean close (the difference comes from the sandbox, spec 3dn); a `link/` directory deleted and recreated by hand while the gateway runs leaves the gateway on the old, stale directory until it is restarted (the daemon itself never removes or recreates `link/` while running; a daemon restart rewrites the files inside it, which the mount shows); the bot token and the pairing are files on disk (0600); a message from the phone carries less authority than input typed at the computer.
10. **Troubleshooting.** A table "message, cause, fix" using the exact strings in the code (section 4 claims), at least: bubblewrap required, daemon not running, not paired, server member limit, `that code is not valid`, `send the code that a2amx team up printed`, `a2amx is not reachable right now`, DNS cannot be resolved, a secure file refused (permissions), `pairing not confirmed`, a code that stopped working after five wrong tries (run `team up` again), `pairing timed out`, and Discord close codes 4013/4014 (intents).
11. **Files.** A table of every file the feature creates or reads, with owner, mode and purpose: `<state>/gateway/{discord.token,config.toml,pairing.json,seen.json}`, `<state>/link/{addr,gateway.token}`, `<state>/gateway.token`, `<state>/addr`.
