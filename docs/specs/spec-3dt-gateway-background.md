## 1. Why

First live Discord test (2026-11-10): `a2amx gateway up` ran in the foreground until Ctrl-C, so closing the terminal stopped the relay and the phone went quiet. The foreground shape was spec 3dm's default, not an owner decision. The owner decided (F84): `gateway up` runs in the background by default like `a2amx daemon start`; `--foreground` keeps today's behaviour; new `gateway stop` and `gateway status`; a log under `<state>/gateway/`; the gateway stays confined. Out of this spec, by the owner's own ordering: how `up --pair` hands over to the background after pairing (spec 3dw; until then `up --pair` runs in the foreground exactly as today).

Design decisions (consultant review, 2026-11-11, applied):

- Liveness and single instance come from an advisory lock, not from a pid file. The launcher takes `flock(LOCK_EX|LOCK_NB)` on `<state>/gateway.lock` (the daemon does the same on `<state>/daemon.lock`, `src/daemon.rs:2290-2303`) and the sandbox keeps the descriptor open, so the lock lives exactly as long as the gateway and frees itself on a crash or SIGKILL: no stale state, no pid reuse window for `status`. The descriptor is opened read-only: `flock` needs no write access, and the sandbox never gets a writable handle to a launcher-owned file.
- The background sandbox does NOT use `--die-with-parent`. That flag is `PR_SET_PDEATHSIG` on the outer bwrap, which fires when the launching process exits, `setsid` or not (probed 2026-11-11, bwrap 0.11.1: a `setsid` bwrap started from a Python parent that exits after 1 s is gone with the flag and alive without it; an earlier shell probe that seemed to show survival was not the real shape). Without the flag, SIGTERM to the outer bwrap pid alone leaves the inner process running, orphaned and still holding the lock, but SIGTERM to the process group ends the whole sandbox (probed); `setsid` makes the outer pid the group id. So the background launch drops the flag and `stop` signals the group. The foreground and `--pair` launches keep the flag (their argv vector does not change), so for them SIGTERM to the outer pid still kills the inner process.
- The pid file is only the target of `stop`. Launcher-owned files (`gateway.lock`, `gateway.pid`) live in `<state>/`, outside the sandbox's one read-write bind (`<state>/gateway/`, `src/gateway_launch.rs:53-63`), so a compromised gateway cannot redirect `stop` to another process. `stop` also verifies the pid's command line before it signals, and signals the process group only when the pid leads its own group (a foreground gateway started by a script may share the script's group).
- The log is `<state>/gateway/gateway.log`, as the owner asked, which is inside that bind: the gateway can replace it. The launcher therefore opens it once, hardened (no symlink, no fifo, a regular file owned by the user with one link), keeps that one open file, passes it to the sandbox as stdout and stderr and reads the startup tail from the same open file (`pread` on the inode the sandbox writes to, never by path again), and sanitizes anything it prints from it.
- The relay logs only errors unless `RUST_LOG` is set (`src/main.rs:113-117`, `EnvFilter::from_default_env()`; the sandbox clears the environment and forwards only the caller's `RUST_LOG`), so a background log would be nearly empty. The background launch defaults the filter to `warn` when the caller sets no `RUST_LOG`.
- `gateway run` already treats SIGTERM as a clean stop (`src/main.rs:354-365`), so the background `stop` is graceful: the signal reaches the inner process through the group, `relay::run` returns, and `seen.json` (written by temp file, fsync and rename, `src/gateway.rs:332-350`) is never torn. A foreground gateway keeps `--die-with-parent`, so a stop of it ends the inner process hard (one duplicate relayed message after a restart is the worst case).

Alternatives rejected: a pid file alone for liveness (stale files, pid reuse, check-then-act races); the daemon supervising the gateway (the gateway is a separate process on purpose, F84); an address-file or socket protocol like the daemon's (the gateway has no listener); log rotation (own backlog row; with a `warn` default the log grows slowly); keeping `--die-with-parent` in the background launch (the sandbox then dies with the launcher); an `--init`-style supervisor process that stays alive (a second process to stop and monitor for no gain); a `stop` that signals only the outer pid (leaves the inner process running).

## 2. `src/gateway_proc.rs` (new): the gateway's process lifecycle

One responsibility: the launcher-side files and checks for a running gateway. It owns the lock, the pid file, the hardened log open, the ready scan, the sanitized tail, `status` and `stop`. It does not build the sandbox (that stays in `gateway_launch`) and does not know Discord.

Constants: `LOCK_FILE = "gateway.lock"`, `PID_FILE = "gateway.pid"` (both under the state directory), `LOG_FILE = "gateway.log"` (under `<state>/gateway/`), `READY_LINE = "gateway ready"`, `READY_WAIT = 10 s`, `STOP_WAIT = 5 s`, `TAIL_LINES = 20`, `TAIL_LINE_CHARS = 200`.

2.1. `pub fn acquire(home: &Path) -> Result<GatewayLock, LockError>`: ensure the state dir (`daemon::ensure_state_dir`), open `<home>/gateway.lock` (`O_RDONLY|O_CREAT|O_NOFOLLOW|O_CLOEXEC`, mode 0600: read-only, unlike the daemon's lock open, so the descriptor the sandbox inherits cannot write the file), `rustix::fs::flock(.., NonBlockingLockExclusive)`. `LockError::Held` when the lock is taken (the caller prints the "already running" message with the pid from the pid file, best effort), `LockError::Other(anyhow::Error)` otherwise. `GatewayLock` owns the `File`; dropping it releases the lock.

2.2. `GatewayLock` exposes `pub fn as_fd(&self) -> BorrowedFd<'_>`: `gateway_launch` clears `FD_CLOEXEC` on that descriptor in the parent just before it spawns the sandbox (rustix `fcntl_setfd`, as `src/session.rs:361-362` already uses it), so the sandbox inherits the lock. Clearing in the parent, not in `pre_exec`, avoids a second `unsafe` descriptor borrow; the launcher spawns nothing else.

2.3. `pub fn write_pid(home: &Path, pid: u32) -> Result<()>`: atomic write (reuse `relay_files::atomic_write`, made `pub(crate)`) of the decimal pid and a newline, mode 0600, to `<home>/gateway.pid`. `fn read_pid(home) -> Option<u32>`: read the file through the same secure read the pairing file uses is not required (the file is launcher-owned, outside every bind); read at most 32 bytes, parse as `u32`, `None` on anything else.

2.4. `pub fn open_log(gateway_dir: &Path) -> Result<(File, u64)>`: `open(<gateway_dir>/gateway.log)` with `O_RDWR|O_APPEND|O_CREAT|O_NOFOLLOW|O_CLOEXEC`, mode 0600; then `fstat` the opened file: it must be a regular file, owned by the effective uid, with `nlink == 1`, else `bail!("refusing to use {path}: not a regular file owned by you with one link")`. Return the file and its current length (the ready scan starts there). A fifo does not block this open (an `O_RDWR` open of a fifo succeeds at once on Linux); the `fstat` check refuses it. The launcher uses this one `File` for the whole launch: `try_clone` for stdout and stderr and for the progress reads.

2.5. `pub fn log_progress(log: &File, from: u64) -> Result<LogProgress>`: read the open file from byte offset `from` with `FileExt::read_at` (at most 64 KiB); `LogProgress { ready: bool, tail: String }`. `ready` is true when any line equals `READY_LINE` exactly. `tail` is `sanitize_tail(bytes)`. It takes the open file, not a path: a path read could be redirected by the gateway to another file in `<state>/gateway/`.

2.6. `pub fn sanitize_tail(bytes: &[u8]) -> String`: decode lossily, keep the last `TAIL_LINES` lines, cut each to `TAIL_LINE_CHARS` characters, replace every control character (including ESC and tab) with `?`. Log text can carry Discord-derived error bodies, so nothing from the log reaches the terminal unsanitized.

2.7. `pub enum State { Running { pid: Option<u32> }, NotRunning }` and `pub fn state(home: &Path) -> Result<State>`: open `<home>/gateway.lock` read-only without creating it (`NotFound` is `NotRunning`: `status` and `stop` do not create the state directory or the file) and try `flock(.., NonBlockingLockExclusive)`; success means nobody holds it (release at once) and the state is `NotRunning`; `EWOULDBLOCK` means `Running { pid: read_pid(home) }`. Known and accepted: the brief check lock can make a concurrent `up` report a false `already running`; a retry succeeds.

2.8. `pub fn stop(home: &Path) -> Result<StopOutcome>` with `StopOutcome::{NotRunning, Stopped { pid }}`:
1. `state(home)`; `NotRunning` returns `NotRunning`.
2. `Running` with `pid == None` is an error: `the gateway is running but gateway.pid is missing or unreadable; stop it by hand (the process whose command line contains "gateway run")`.
3. Verify the process: read `/proc/<pid>/cmdline` (at most 64 KiB, NUL-separated); it must contain, as consecutive elements, `--home`, the canonical state directory (`fs::canonicalize(home)`, as `up` puts into the sandbox argv), `gateway`, `run`. If `/proc/<pid>` does not exist while the lock is held, the outer process was killed and its inner process is orphaned: error `the gateway holds the lock but its process N is gone (killed by hand?); end it with: kill -TERM -- -N` (the group id is the pid, `setsid` made it so; the command is printed for the owner, nothing is signalled). Any other failure to verify (the file is unreadable or does not match) is an error: `refusing to signal pid N: it is not the gateway for this state directory` and nothing is signalled.
4. Signal: `getpgid(pid) == pid` (the gateway leads its own group, as a background launch makes it): `rustix::process::kill_process_group(pid, Signal::TERM)`; otherwise (a foreground gateway that shares its starter's group) `rustix::process::kill_process(pid, Signal::TERM)` to the pid alone, which ends the inner process because the foreground sandbox keeps `--die-with-parent`. `ESRCH` counts as already gone. Never signal a group the caller itself belongs to.
5. Poll the lock (`state`) every 100 ms for `STOP_WAIT`; when it is free the gateway is gone: remove `gateway.pid` (ignore `NotFound`), return `Stopped { pid }`. After the wait, error `the gateway (pid N) did not stop within 5s`; no SIGKILL.

`shortcut:` comment on step 3: the check is a command-line match, so a process that copies the gateway's arguments passes it; it is not authentication, only a guard against a stale pid file. The pid file is outside the sandbox bind, which is what keeps it trustworthy.
