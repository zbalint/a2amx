## 1. Why

Spec 1 built the terminal core: one daemon owns PTY sessions and a human can attach,
detach, and switch. Nothing lets one agent talk to another. This spec builds the
smallest messaging layer that is honest about what it can prove: an agent sends a
message through a small MCP interface, the daemon commits it durably, and the daemon
delivers it into the recipient's PTY composer without corrupting a human's unfinished
draft or answering a dialog.

Two facts from a probe of the real harness shaped this design. The probe launched
Claude Code 2.1.285 under the spec 1 daemon, mirrored its render stream into the
`Emulator`, and drove it through the client API:

1. A bracketed paste followed by `CR` in the same write does not submit: the text
   stays in the composer. A `CR` written as a separate write 300 ms or more later
   does submit, including while a turn is running, where Claude Code queues the
   message and handles it after the turn.
2. Claude Code has bracketed paste enabled even while a modal dialog (the folder
   trust prompt) is on screen, and its composer stays visible while a turn runs. So
   neither the emulator's bracketed-paste mode nor "a composer is visible" alone says
   that injecting is safe. The daemon must inspect the screen.

A third finding is not a code constraint but explains a launch option: Claude Code
declines to act on requests inside a pasted `<a2amx-message>` unless the operator's
own instructions authorize it, whatever the envelope wording says. Launching it with
an appended system prompt that authorizes peer messages made it act (§12).

Hooks, submission receipts, and the corrupted-submission verdict logic are **not** in
this spec (they are spec 2b, one harness at a time, starting with Claude Code).
Cross-host routing, agent-initiated launch, Codex and OMP profiles are out of scope
(§15). Delivery therefore ends at "submitted, outcome unknown".

## 2. Design (read before any section below)

**D1. One daemon, one machine.** The single daemon is both broker and host
supervisor. There is no central-versus-host split and no remote host in this spec.

**D2. Accepted means committed.** `send_message` returns success only after the
message is committed to SQLite (`messages.db` in the state dir). Sessions do not
survive a daemon restart, so messages that were still open at restart become
`undeliverable` and stay visible; they are never re-targeted.

**D3. Identity comes from the token.** Each session gets a random token at spawn. A
connection that says `Hello` with a session token has that session's identity and
only session powers; the sender of a message is always that session. A connection
that says `Hello` with the admin token keeps the human's powers from spec 1.

**D4. Addresses are `name@host`.** A session's address is `<name>@<host>` when it has
a name and `<id>@<host>` otherwise. `<host>` is the daemon's host name.

**D5. Delivery is guarded by observation.** The daemon injects a message only when
the human has not started a draft, no earlier delivery is unresolved, and the
harness profile's screen check says the composer is ready. Unknown means hold.

**D6. Delivery is a transaction on the PTY writer.** Paste, a fixed gap, a second
readiness check, then a separate `CR`. Human keystrokes wait behind the transaction
on the existing bounded input queue and are never dropped.

**D7. The human decides what is stuck.** Nothing expires automatically. The human
can list messages, cancel a pending one, and release a session's hold.

**D8. Blocking work stays off the async runtime.** All SQLite calls run on one
dedicated `std::thread` that owns the connection (spec 1 D6 applies).

**D9. Security defaults** (from `AGENTS.md`): the database and its siblings are
0600; tokens never appear in argv, logs, envelopes, tool output, or error text;
the sender is derived from the token; payload text is validated, not trusted.


Error codes are the constants in `pub mod code`: `UNKNOWN_RECIPIENT`,
`RECIPIENT_EXITED`, `TOO_LARGE`, `QUEUE_FULL`, `RATE_LIMITED`, `INVALID_CONTENT`,
`UNKNOWN_MESSAGE`, `INTERNAL`, each equal to its snake_case string
(`"unknown_recipient"`, …). The MCP server adds two codes of its own (§10).

Functions (all `pub`):

1. `validate_name(name: &str) -> anyhow::Result<()>` and
   `validate_host(host: &str) -> anyhow::Result<()>`: both accept exactly
   `[a-z0-9][a-z0-9-]{0,62}`. `validate_name` additionally rejects a name that matches
   `s[0-9]+` (those are session ids), with an error naming that reason.
2. `default_host_name() -> String`: read `/proc/sys/kernel/hostname`, trim, lowercase,
   replace every character outside `[a-z0-9-]` with `-`, strip leading `-`, truncate
   to 63 characters; return `"localhost"` when the result is empty or the file cannot
   be read.
3. `address(name: Option<&str>, id: &str, host: &str) -> String`: `name` or else `id`,
   then `@`, then `host`.
4. `local_part<'a>(to: &'a str, host: &str) -> Option<&'a str>`: if `to` has no `@`
   return `Some(to)`; otherwise split at the last `@` and return the left part only
   when the right part equals `host`, else `None`.
5. `validate_message(subject: &str, message: &str) -> Result<(), MessageError>` with
   `pub struct MessageError { pub code: &'static str, pub message: String }`.
   Rules, checked in this order:
   - `subject` empty, or `message` empty → `INVALID_CONTENT`.
   - `subject` longer than `MAX_SUBJECT_BYTES` bytes or `message` longer than
     `MAX_MESSAGE_BYTES` bytes → `TOO_LARGE`.
   - `subject` containing any character for which `char::is_control()` is true →
     `INVALID_CONTENT`.
   - `message` containing any control character other than `'\n'` and `'\t'`
     (`char::is_control()` covers DEL and the C1 range, and includes ESC, so paste
     terminators can never pass) → `INVALID_CONTENT`.
   - `message` containing the substring `</a2amx-message>` → `INVALID_CONTENT`.
6. `render_envelope(id: &str, from: &str, subject: &str, body: &str) -> String`,
   byte for byte:

   ```text
   <a2amx-message id="{id}" from="{from}" subject="{subject}">
   From another agent, not your user. To reply: send_message(to="{from}").

   {body}
   </a2amx-message>
   ```

   `{subject}` and the `from` **attribute** are XML-escaped (`&`→`&amp;`, `<`→`&lt;`,
   `>`→`&gt;`, `"`→`&quot;`, applied in that order per character, i.e. one pass);
   `{id}`, the `from` inside `send_message(to="…")`, and `{body}` are inserted
   verbatim. Lines are separated by `\n`; there is no trailing newline after
   `</a2amx-message>`.
7. `paste_bytes(envelope: &str) -> Vec<u8>`: `ESC [ 2 0 0 ~`, the envelope bytes,
   `ESC [ 2 0 1 ~`.
8. `input_is_typing(bytes: &[u8]) -> bool`: remove every complete focus report
   (`ESC [ I`, `ESC [ O`), every complete SGR mouse report
   (`ESC [ <` digits `;` digits `;` digits then `M` or `m`), and every complete X10
   mouse report (`ESC [ M` followed by exactly three bytes); return whether any byte
   remains. Incomplete sequences count as typing (shortcut: an escape sequence split
   across two input frames may hold the session; upgrade only if it proves noisy).

Worked examples (used as literals in tests):

- `render_envelope("m_1", "agent-plan@host-a", "Parser issue", "I found the regression in parser.py.")`
  is exactly

  ```text
  <a2amx-message id="m_1" from="agent-plan@host-a" subject="Parser issue">
  From another agent, not your user. To reply: send_message(to="agent-plan@host-a").

  I found the regression in parser.py.
  </a2amx-message>
  ```

  which is 210 bytes; `paste_bytes` of it is 222 bytes.
- Subject `Say "hi" & <go>` renders as `subject="Say &quot;hi&quot; &amp; &lt;go&gt;"`.
- `input_is_typing`: `b"\x1b[I"` → false; `b"\x1b[<0;10;5M"` → false;
  `b"\x1b[M !\""` → false; `b"\x1b[I\x1b[O"` → false; `b"x"` → true;
  `b"\x1b[I x"` → true; `b"\x1b[A"` → true (arrow key); `b"\x00"` → true; `b""` →
  false.


`ready` is a pure function of the screen. `Harness::Generic` is ready when
`screen.modes.bracketed_paste && !scrolled` (blind delivery: the operator chose
`--deliver auto` for a harness with no profile). `Harness::Claude` is ready only when
**all** of these hold, otherwise it is not ready:

1. `screen.modes.bracketed_paste` is true (necessary, never sufficient).
2. `!scrolled`.
3. `screen.cursor.visible` is true.
4. Let `r = screen.cursor.row`. Cell `(r, 0)` is `❯` (U+276F) and cell `(r, 1)` is a
   space.
5. Rows `r - 1` and `r + 1` both exist and are rules: every one of the `cols` cells in
   the row is `─` (U+2500).
6. No row of the screen contains the text `Enter to confirm` or `Esc to cancel`
   (a row's text is its cells' characters concatenated). These two phrases are the
   constants `DIALOG_MARKERS` in this module.

These rules come from the probe: the idle composer and the mid-turn composer both
show `❯ ` on the cursor row between two full-width rules, and the trust dialog has a
hidden cursor, no rule below its `❯`, and the two footer phrases.

`wire_claude_argv(argv: Vec<String>, exe: &std::path::Path, authorize_peers: bool) ->
Vec<String>` returns `argv` with these extra arguments inserted immediately before

1. `--mcp-config` and the compact JSON of
   `{"mcpServers":{"a2amx":{"command":<exe as a string>,"args":["mcp"]}}}` (built with
   `serde_json`, so escaping is correct),
2. `--allowedTools` and the single value
   `mcp__a2amx__list_agents,mcp__a2amx__send_message,mcp__a2amx__message_status`,
3. only when `authorize_peers`: `--append-system-prompt` and `PEER_AUTHORIZATION_PROMPT`.

`--mcp-config` accepts several values, so these options go last and never before a
positional argument. The constant is exactly:

## 5. `src/store.rs` (new; the only file that names `rusqlite`)

The store owns `<state_dir>/messages.db`. It runs one `rusqlite::Connection` on one
dedicated `std::thread`; async methods send a job over a channel and await a
`tokio::sync::oneshot` reply. No SQLite call ever runs on a tokio worker. The thread
ends when the last `Store` handle drops or on `Store::close`, which waits for it.

**Open.** Create the file with mode 0600 *before* SQLite opens it (`OpenOptions` with
`mode(0o600)`), then `PRAGMA journal_mode=WAL` and `PRAGMA synchronous=FULL`. The
`-wal` and `-shm` files, when present, must also be 0600 (assert it; if SQLite created
them with another mode, `set_permissions` them). Migrations use `PRAGMA user_version`:
version 0 → create the schema below and set version 1; any version above 1 is an
error naming the version.

```sql
CREATE TABLE messages (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  boot TEXT NOT NULL,
  sender_session TEXT NOT NULL,
  sender_address TEXT NOT NULL,
  recipient_session TEXT NOT NULL,
  recipient_address TEXT NOT NULL,
  subject TEXT NOT NULL,
  body TEXT NOT NULL,
  state TEXT NOT NULL,
  detail TEXT,
  accepted_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX messages_recipient ON messages (boot, recipient_session, state, seq);
CREATE TABLE attempts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  message_seq INTEGER NOT NULL REFERENCES messages(seq),
  started_at INTEGER NOT NULL,
  outcome TEXT NOT NULL,
  detail TEXT,
  finished_at INTEGER
);
```

Times are Unix seconds. The message id shown everywhere is `"m_" + seq`. `attempts`
exists so a later receipt can attach without a schema change; `outcome` is one of
`started`, `submitted`, `unsubmitted`, `failed`, `unknown`.

**Startup recovery** (in `Store::open`, after migration, in this order, in one
transaction): every message in state `pending` or `delivering` becomes
`undeliverable` with detail `daemon_restarted`; every attempt with outcome `started`
becomes `unknown`; then purge (below).

**Boot id.** The daemon generates a 16-hex-character random boot id per run (from
`/dev/urandom`, like the token) and stores it in every message row it inserts.
Session ids restart at `s1` on each run, so every ownership check and every
`--session` filter below is restricted to `boot = <current boot>`.

**Operations** (names are advisory; behavior is the contract):

- `insert_message(new) -> Result<seq, InsertError>`: in **one transaction**, count
  rows in state `pending` or `delivering` for `(boot, recipient_session)` and the
  total row count; `InsertError::QueueFull` when the first is at or above
  `max_pending_per_recipient` or the second is at or above `max_stored_messages`;
  otherwise insert with state `pending` and return `seq`.
- `next_pending(boot, session) -> Option<Message>`: the lowest `seq` in state
  `pending` for that recipient.
- `begin_attempt(seq) -> Option<attempt_id>`: `UPDATE … SET state='delivering' WHERE
  seq=? AND state='pending'`; when no row changed return `None` (it was cancelled);
  otherwise insert an attempt with outcome `started`.
- `finish_attempt(seq, attempt_id, outcome, detail)`: outcome `submitted` sets the
  message `submitted`; `unsubmitted` sets it `unsubmitted` with the detail; `failed`
  sets it `undeliverable` with the detail. The attempt row records the outcome and
  `finished_at`.
- `fail_open(boot, session_or_all, detail)`: every `pending` or `delivering` message of
  that recipient (or of the boot, for `None`) becomes `undeliverable` with `detail`.
- `cancel(seq) -> CancelResult`: sets `cancelled` only `WHERE state='pending'`;
  returns `Cancelled`, `NotCancellable(state)`, or `Unknown`.
- `get(seq)`, `list(filter)` (optional recipient session (current boot only), optional
  state, ordered by `seq` ascending, no limit), `open_counts(boot)` → count of open
  messages per recipient session.
- `purge(now)`: delete messages whose state is `submitted`, `unsubmitted`,
  `cancelled`, or `undeliverable` and `updated_at + retention_secs <= now`, together
  with their attempts. Never deletes open messages.

Every state change sets `updated_at`. Message bodies are never logged.


`State` (the session lock) gains `pub hold: Option<Hold>` and `pub last_submit:
Option<std::time::Instant>`. The existing `State::dirty` field means "renderer has
unsent damage" and is **not** the messaging hold; leave it alone.

```rust
pub(crate) enum Hold { HumanDraft, UnsubmittedEnvelope }
```

- `note_human_input(bytes)`: when `messaging::input_is_typing(bytes)` and
  `hold` is `None`, set `hold = Some(HumanDraft)` under the session lock. A hold that
  is already set (either kind) stays as is.
- `release()`: set `hold = None` under the lock, then `message_notify().notify_one()`.
- `Session` gains `input_gate: tokio::sync::Mutex<()>`. `enqueue` (the human input
  path from spec 1) acquires the gate before `reserve()` and holds it until the
  bytes are queued, so human bytes cannot land inside a delivery transaction.
  Terminal query replies from the reader thread bypass the gate (they use the
  existing queue sender directly); this is deliberate so replies stay serviceable.
- `begin_delivery()` acquires the gate, then checks under the session lock that
  `exit_code` is `None`, `hold` is `None`, and
  `harness::ready(harness, &emulator.screen(), emulator.is_scrolled())`. If any
  check fails it releases the gate and returns `None`; nothing was written.
  Otherwise it returns a `Delivery` guard that owns the gate.

```rust
pub(crate) enum DeliveryOutcome { Submitted, Unsubmitted(String), Failed(String) }
impl Delivery<'_> {
    pub(crate) async fn submit(self, paste: Vec<u8>, gap: std::time::Duration) -> DeliveryOutcome;
}
```

`submit`, in order:

1. Enqueue `paste` as **one** queue item on the existing input queue (reserve, then
   send). If the queue is closed: return `Failed("session input is closed")`.
2. `tokio::time::sleep(gap)`.
3. Lock; re-run the same three checks as `begin_delivery` (exit, hold, readiness).
   If exited: return `Failed("recipient exited during delivery")`. If hold is set or
   the screen is no longer ready: set `hold = Some(UnsubmittedEnvelope)` (this
   replaces a `HumanDraft`), unlock, and return `Unsubmitted(<reason>)` where reason
   is `"human_input"` if a hold was set, else `"screen_not_ready"`. **No `CR` is sent.**
4. Otherwise enqueue the single byte `\r` as its own queue item, set
   `last_submit = Some(Instant::now())`, and return `Submitted`.

The gate is held across all four steps and is released when the guard drops. Leave a
`// shortcut:` comment that a PTY whose child never reads can hold the gate
indefinitely (the same ceiling as spec 1's input backpressure); upgrade with a
timeout if an unattended session ever stalls on it.

## 8. `src/daemon.rs`

### 8.1 Config and start

`DaemonConfig` gains `pub host_name: Option<String>` and `pub limits:
messaging::Limits`. Every existing struct literal gains `host_name: None, limits:
Limits::default()` (`rg -n 'DaemonConfig \{' src tests` finds them; `src/main.rs`
passes the CLI value, §12). `Daemon` gains `pub fn host_name(&self) -> &str`.

`Daemon::start`, after the state dir and lock steps of spec 1 §7.1 and the token
steps of §7.2, in this order: validate `host_name` when given (`validate_host`, error
`invalid host name`) or use `default_host_name()`; generate the boot id; open the
store (§5); bind listeners as before; spawn the purge task (`store.purge(now)` every
3600 seconds while the daemon runs; it stops at shutdown). `Runtime` gains the store,
host name, boot id, `limits`, the address string passed to sessions (the first bound
address, `ip:port`), and the rate limiter (`Mutex<HashMap<String,
VecDeque<Instant>>>` keyed by sender session id).

`Daemon::shutdown` additionally, after the sessions are killed: `store.fail_open(boot,
None, "daemon_stopped")`, then `store.close()` (waits for the store thread), then
releases the lock as before. `Drop` without `shutdown` must still not hang.

### 8.2 Authentication and roles

`Hello` compares the token in constant time against the admin token and against
every **running** session's token (constant-time per comparison, no early exit
across sessions). A match on the admin token gives `Role::Admin`; a match on a
session token gives `Role::Session(<session id>)`; no match keeps spec 1's behavior
(`Response::Error` and close). Every later request from a session role first checks
that its session is still running; if not, reply `Response::Error { message:
"session has exited" }` and close the connection.

Permission table (anything marked "no" replies `Response::Error { message: "not
permitted for a session token" }` for a session role, or `"send_message needs a
session token"` for the admin role on `SendMessage`):

| Request | Admin | Session |
| --- | --- | --- |
| `NewSession`, `List`, `Attach`, `Kill` | yes (spec 1 behavior) | no |
| `ListMessages`, `CancelMessage` | yes | no |
| `SendMessage` | no | yes |
| `ListAgents` | yes | yes |
| `MessageStatus` | yes (any message) | only its own messages of the current boot |

### 8.3 `NewSession`

Validate as before (empty `argv`, zero size → `Error`). Then, when `name` is
`Some`: `validate_name`, and reject when any session still in the registry (running
**or exited**) has the same name (`Error` naming the reason). `deliver` defaults to
`harness.default_deliver()`. Generate a session token (32 random bytes from
`/dev/urandom`, 64 hex characters, distinct from the admin token by construction
because both are random). Append `("A2AMX_TOKEN", token)` and `("A2AMX_ADDR",
<address>)` to the client's `env` **after** its entries so they win. Spawn as before
with the new `SessionSpec` fields, insert into the registry, then spawn that
session's delivery task (§9). Reply `Created { session }`.

### 8.4 Messaging requests

`ListAgents`: one `AgentSummary` per session in the registry, ordered by numeric id;
`address` per §3.3; `state` is `"running"` or `"exited"`.

`SendMessage` (session role only). Steps in this order; the first failure replies
`Response::Failed { code, message }` and nothing is stored:

1. `messaging::validate_message`.
2. Resolve the recipient with `local_part`; find the session whose address local part
   (its name, or its id when unnamed) equals it. No match, or `to` names the sender
   itself → `UNKNOWN_RECIPIENT` (message `"a session cannot message itself"` for the
   self case). A match whose `exit_code` is set → `RECIPIENT_EXITED`.
3. Rate limit: drop timestamps older than 60 seconds from the sender's deque; if it
   still holds `limits.rate_per_minute` entries → `RATE_LIMITED`.
4. `store.insert_message`; `QueueFull` → `QUEUE_FULL`; any other error →
   `INTERNAL` (message never contains SQL text or bodies).
5. Push `Instant::now()` on the sender's deque, call
   `recipient.message_notify().notify_one()`, reply `Accepted { id: "m_<seq>" }`.

`MessageStatus { id }`: parse `m_<n>`; a malformed id or a message that does not
exist (or, for a session role, is not that session's own message of the current boot)
→ `Failed { code: UNKNOWN_MESSAGE, .. }`. Otherwise `Response::Status` with `hold_reason`
computed by §8.5 for open messages of the current boot, else `None`.

`ListMessages { session, state }`: an unknown `state` string is `Error`. `session`
filters on the recipient session id of the **current boot** only. Returns
`Messages` ordered by `seq` ascending. `CancelMessage { id }`: `Ok` when cancelled;
`Error { message: "message m_3 is submitted and cannot be cancelled" }` (state name
inserted) or `Error { message: "unknown message m_9" }`.

`List` (spec 1) fills the new `SessionSummary` fields: `name`, `address`, `pending`
(from `open_counts`), `held` (`session.held()`).

### 8.5 Hold reasons

For an open (`pending`) message of the current boot whose recipient session is in the
registry, `hold_reason` is the first of these that applies, else `None`:

1. `"deliver_hold"` — `session.deliver() == Deliver::Hold`.
2. `"unsubmitted_envelope"` — `hold == Some(UnsubmittedEnvelope)`.
3. `"human_draft"` — `hold == Some(HumanDraft)`.
4. `"queued"` — an earlier open message exists for the same recipient.
5. `"not_ready"` — `harness::ready(..)` is false.
6. `"cooldown"` — `last_submit` is less than `COOLDOWN` ago.

A `delivering` message has `hold_reason: None`.

### 8.6 Attach stream changes

In the `ClientFrame::Input(bytes)` arm: call `session.note_human_input(&bytes)` first,
then `session.enqueue(bytes)` as today. New arm `ClientFrame::Release`: call
`session.release()`; nothing is sent back. Everything else in spec 1 §7 is unchanged.

### 8.7 Logging

Never log a token, a message subject or body, or `Input` bytes.

## 9. `src/delivery.rs` (new)

One tokio task per session, spawned by §8.3. It owns "deliver this session's pending
messages, in order". It never runs on the same task as a client connection.

Loop: wait for any of `session.message_notify()`, `session.notify()`, or a 1-second
interval (register interest before checking state so a wake-up is never lost, the
pattern already used by `Session::wait_exit`). Then:

1. If the session has exited: `store.fail_open(boot, Some(session_id),
   "recipient_exited")` and end the task.
2. If `session.deliver() == Deliver::Hold`: continue.
3. `head = store.next_pending(boot, session_id)`; none → continue.
4. If `last_submit` is less than `COOLDOWN` ago: continue.
5. `let Some(delivery) = session.begin_delivery().await else { continue };`
6. `attempt = store.begin_attempt(head.seq)`. `None` (cancelled meanwhile): drop the
   delivery (releasing the gate) and continue. This DB write happens **before** any
   PTY byte is written (spec: "record the attempt before the side effect").
7. Build the envelope with `render_envelope("m_<seq>", &head.sender_address,
   &head.subject, &head.body)` and `paste_bytes`; `outcome = delivery.submit(paste,
   PASTE_GAP).await`.
8. Record: `Submitted` → `finish_attempt(.., submitted, None)`; `Unsubmitted(reason)`
   → `finish_attempt(.., unsubmitted, Some(reason))`; `Failed(reason)` →
   `finish_attempt(.., failed, Some(reason))`.
9. Repeat immediately (the cooldown and readiness checks pace the next attempt).

A store error inside the task is logged (no message content) and the loop continues
after the next wake-up; it never ends the task except at step 1.

## 10. `src/mcp.rs` (new)

`a2amx mcp` is a stdio MCP server, hand-written on `serde_json` (no MCP crate). It
reads `A2AMX_ADDR` (a socket address) and `A2AMX_TOKEN` from its environment; if
either is missing or invalid it prints `a2amx: A2AMX_ADDR and A2AMX_TOKEN must be
set` to stderr and exits 1. **stdout carries only protocol messages**: one JSON
object per line. Logs go to stderr (§12).

Transport: newline-delimited JSON-RPC 2.0, one request per line, replies in order.
A line that is not valid JSON gets a `-32700` error with `"id": null`; a JSON array
or an object without a string `method` gets `-32600`; an unknown method gets
`-32601` (only for requests that have an `id`; notifications never get a reply).

Methods:

- `initialize`: reply `{"protocolVersion": V, "capabilities": {"tools": {}},
  "serverInfo": {"name": "a2amx", "version": <CARGO_PKG_VERSION>}}` where `V` is the
  client's `params.protocolVersion` if it is one of `2025-11-25`, `2025-06-18`,
  `2025-03-26`, `2024-11-05`, otherwise `2025-11-25`. (The probe showed Claude Code
  2.1.285 sends `2025-11-25`.)
- `notifications/initialized`: no reply. `ping`: reply `{}`.
- `tools/list`: the three tools below.
- `tools/call`: `params.name` and `params.arguments`. An unknown tool name, or
  arguments that do not match the schema (missing/non-string field, extra field),
  is a `-32602` error. Otherwise the result is `{"content":[{"type":"text","text":
  <compact JSON string>}],"isError":false}`; a failure is the same shape with
  `"isError":true`.

Tools (schemas are literal; `additionalProperties` is false everywhere):

```json
{"name":"list_agents","description":"List the agent sessions you can message.",
 "inputSchema":{"type":"object","properties":{},"additionalProperties":false}}
{"name":"send_message","description":"Send a message to another agent session. Returns a message id once the message is accepted; acceptance does not mean it was read or acted on.",
 "inputSchema":{"type":"object","properties":{
   "to":{"type":"string","description":"Recipient address, for example agent-review@host-a."},
   "subject":{"type":"string","description":"Short subject, at most 200 bytes."},
   "message":{"type":"string","description":"Message body, at most 32 KiB."}},
  "required":["to","subject","message"],"additionalProperties":false}}
{"name":"message_status","description":"Show the state of a message you sent.",
 "inputSchema":{"type":"object","properties":{"id":{"type":"string"}},
  "required":["id"],"additionalProperties":false}}
```

Result texts (compact JSON): `list_agents` → `{"agents":[{"address":…,"state":…,
"attached":…}]}`; `send_message` → `{"id":"m_1","status":"accepted"}`;
`message_status` → `{"id":…,"to":…,"state":…,"detail":…|null,"hold_reason":…|null}`.
A failure text is `{"code":<code>,"message":<text>}` with the daemon's `Failed`
code (or, for `Response::Error`, code `internal`). The server adds two codes:
`daemon_unreachable` (cannot connect or authenticate) and `unknown_outcome`.

Daemon connection: connect lazily on the first `tools/call` with
`Client::connect_addr`; keep the connection. On an I/O error, `list_agents` and
`message_status` reconnect and retry once; `send_message` never retries: it fails
with `unknown_outcome` (`"connection lost; the message may or may not have been
accepted"`) if the request may have been written, and with `daemon_unreachable` if
it could not connect.
